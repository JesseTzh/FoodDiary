# Web 性能优化报告

测试日期：2026-11-07。基线提交：`bfeca2cd594ea8e8688d934348106b076b12e94a`。优化版本为本次工作区改动，尚未提交或部署。

## 结论与瓶颈

Android 原生 App 流畅，不代表同一套 Flutter 界面在浏览器中的绘制成本相同。本次对照发现，Web 的主要可优化项集中在渲染器选择、卡片绘制、照片尺寸、初次资源传输和返回转场；返回过程没有产生 API 请求，测试中的停顿不来自重新请求菜单数据。

| 原因与证据 | 已落实的优化 |
| --- | --- |
| 原发布配置强制 CanvasKit，无法使用当前 SDK 支持的 skwasm 路径 | 构建 Wasm 与 JavaScript 回退，由 Flutter 选择兼容引擎；Go 返回跨源隔离头 |
| 列表反复绘制大模糊阴影；高 DPR 卡片直接跨到 1024px 照片 | Web 卡片改为细边框；新增 640px 中档，根据实际像素和裁剪范围选图 |
| Web 全屏相册一打开便下载、解码原图 | 初始使用 1024px 预览，双指放大后加载原图，切换时保留旧画面 |
| 中文 TTF 17.77MB，六张 PNG 7.30MB；原后端未提供本次新增的压缩传输 | 原 TTF 使用 HTTP Brotli/gzip；Web 图片转换为逐像素一致的无损 WebP |
| 原页面转场存在约 500ms 的返回等待，iOS Web 还带 Flutter 的边缘交互机制 | Web 前进改为 120ms 淡入、返回时长为零；取消 Web 内部 Cupertino 边缘手势 |
| Service Worker 安装时预缓存全部引擎变体，照片过期后等待网络 | 首帧后空闲注册、缩减预缓存，过期照片立即展示缓存并后台刷新 |
| 成功加载后先序列化并写入本地快照，再显示页面 | 先显示数据，下一帧后保存；存储失败不再使成功加载进入错误状态 |

这些是成组改动的对照，不能把总收益分别归因到某一项，也不能据此声称 Android 原生性能存在问题。原生转场、原始 PNG 素材和原生相册原图行为保留；640px 照片档位为共享改进。

## 测试口径

使用两个独立 Release 目录，基线从上述提交构建，优化版通过实际 `scripts/build-web.sh` 构建。macOS 27.0.1 / arm64，Chrome 156.0.8078.81，视口 390×844、DPR 3。每组各运行三次，取中位数。每次使用全新浏览器上下文，统一注入 300 条合成日记、300 条合成菜谱与固定 JPEG；无生产账号、业务记录或用户照片参与。

GPU 路径与兼容选择路径使用 4 倍 CPU 限速；禁用 WebGL 的 CPU 绘制路径不额外限速。运行前后测试依次执行，避免互相争用资源。基线本地服务按原后端行为提供未压缩文件，优化服务协商构建生成的压缩文件并添加隔离头；未限制网络带宽，因此启动数据主要描述本机加载、解析、初始化时间，不能直接代表移动网络加载时间。

启动就绪：从导航开始，到首页记录按钮在 Flutter 语义树中可见；两组均启用语义树以定位操作。滚动：同一菜谱页连续 40 次相同滚轮输入，记录 rAF 间隔与超过 50ms 的 Long Task。返回：调用 `history.back()` 到首页按钮重新可见。这个操作覆盖浏览器历史到 Flutter 的返回链路，**不包含 iPhone 系统手势动画与 WebKit 快照恢复时间**。

rAF 是主线程回调间隔，**不是画面实际呈现的 GPU FPS**。`gapsOver33ms` 实际以 >33.4ms 统计，避免把正常 30Hz 采样浮点误差算作额外卡顿。`--ios` 同时替换 UA/vendor，仅用于触发 SDK 的 Safari 兼容选择，底层仍是 Chromium，不能称为 Safari/iPhone 真机测试。软件路径主动禁用 WebGL，是降级情景，不代表所有设备的通常表现。

性能隔离测试关闭 Service Worker，避免新旧缓存干扰；PWA 另在真实 Go 后端上验证在线安装、接管和断网重载。

## 资源优化与实际取舍

六张 WebP 逐张解码后比较 RGBA 字节，与原始 PNG 一致，没有缩小图片或损失透明度。照片的 640px 档位保留长宽比，并按归一化裁剪范围提高所需分辨率；对 1024×1024 与 640×640 方图，解码像素数量理论上减少 60.9%，这不等于实测浏览器总内存降低 60.9%。

本次试验过 WOFF2，但在 4 倍 CPU 限速下出现约 1.4 秒的字体首次使用主线程停顿，启动约 4.7 秒。该方案已撤销，最终保留 TTF，用网络层 Brotli 压缩，未删中文字形。这个探索数据不是正式前后对照结果。

发布文件夹会变大，因为同时保留兼容引擎、PNG 与 WebP、原文件与压缩副本。磁盘占用增长不能作为下载量增长；Service Worker 不会分别下载 `.br`/`.gz` 副本。预缓存仍保留默认 CanvasKit、Chromium CanvasKit、skwasm 三类必要文件，兼容切换可离线工作。

Web 卡片的轻微阴影改为边框是可见样式变化；前进动画缩短，返回不再播放额外淡出。已对照截图检查中文、图片、列表布局，实际浏览器请求未出现字体解析失败或资源 404。

## iPhone 主屏幕 PWA 左滑返回

你提供的“按钮返回快、只有系统侧滑慢”说明需要区分系统手势/历史交接和应用内部绘制。代码中可以消除的额外返回转场和 Flutter 边缘手势已经处理；浏览器历史测试也确认返回不触发 API 重新加载。因此这是导航交接/转场问题的重要线索，不能仅归类为服务器慢或菜单加载慢。

**尚未进行真实 iPhone 安装式 PWA 的系统侧滑测试，所以不能确认其长停顿已经完全消失，也不能报告其实际提速百分比。** CanvasKit 兼容数据独立列出，不能用 Chrome skwasm 的启动收益替代。真机验收应在部署新版并激活更新后，比较同一详情页的按钮返回、系统边缘侧滑返回，以及返回前后是否有网络请求；若仍有长停顿，需要通过 Mac Safari 远程检查记录手势释放、popstate 与上级页首帧的时间，确定延迟发生于 WebKit 交接前还是 Flutter 内部。

## 复现与部署

构建依赖见 `scripts/requirements-web.txt`，建议在 Python 虚拟环境安装。Docker 和 CI 已接入相同流程。使用当前项目 Flutter SDK（本次为 3.47.7），从仓库根目录执行：

```sh
python3 -m pip install -r scripts/requirements-web.txt
bash scripts/build-web.sh --output=/tmp/fooddiary-after
python3 scripts/ci/web/performance-fixtures.py frontend/assets/images/tomato-scrambled-eggs.png /tmp/fooddiary-fixtures
npm ci --prefix scripts/ci/web
node scripts/ci/web/performance.mjs --build=/tmp/fooddiary-after --fixtures=/tmp/fooddiary-fixtures --output=/tmp/after.json --runs=3 --cpu=4 --channel=chrome --delivery=optimized
```

基线在独立 checkout 中使用基线自带 `scripts/build-web.sh` 构建，随后用当前性能脚本运行，去掉 `--delivery=optimized`。兼容选择组追加 `--ios`；软件组追加 `--software` 并去掉 `--cpu=4`。需要安装可用的 Google Chrome；也可调整浏览器 channel。基准服务仅使用合成数据与临时本地端口，不依赖生产后端。

离线测试必须指向一次性本地后端，它会设置或使用测试密码：

```sh
CI_BASE_URL=http://127.0.0.1:18764 CI_BROWSER_CHANNEL=chrome node scripts/ci/web/offline.mjs
node --test scripts/ci/web/photo-cache.test.mjs
```

部署需同时更新 Web 文件和 Go 后端，才能获得压缩传输与跨源隔离收益。反向代理应保留 `Content-Encoding`、`Vary`、`.wasm`/`.mjs` MIME、`Cross-Origin-Opener-Policy: same-origin` 和 `Cross-Origin-Embedder-Policy: require-corp`；自定义静态托管需配置等价行为。新增外域字体、图片或脚本时需要确认其满足 COEP 资源加载要求。更新前已有 PWA 缓存仍会继续服务旧版，需等待新版安装并点击应用内刷新提示；不能仅替换服务器文件后立即以旧 PWA 的表现判断优化无效。

优化不改变全量业务 API 的数据规模。本次基准覆盖 300 条日记与 300 条菜谱；更多记录、更大原图、真实手机温度/电量和 WebKit 系统手势仍可能产生不同结果，应按真实数据继续测量，不能承诺所有 Web 场景均已无性能瓶颈。
